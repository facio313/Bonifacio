# Bonifacio operating contract

- `https://bonifacio.work/sso/` is the single sign-on portal for the portfolio services hosted on `bonifacio.work`.
- Authelia `AuthRequest` is the authoritative edge session. Protected upstreams receive `Remote-User`, `Remote-Email`, `Remote-Name`, and `Remote-Groups` only after the host Nginx auth subrequest succeeds.
- The edge must overwrite, never append or trust, caller-supplied `Remote-*` headers. Application origins remain loopback-only or Docker-internal so they cannot be used to bypass the edge.
- The SSO portal, its internal authorization endpoint, and narrow container/deployment health probes are the only infrastructure exceptions to the login gate. A product's explicitly public share route may remain public only where that repository contract requires it.
- Authelia configuration is committed without secrets. The real user database, session/encryption/reset secrets, SQLite state, Redis state, and notification file stay outside Git in operator-owned paths or named volumes.
- The deployment is one-factor and file-backed. Public self-registration, email password reset, and Authelia's independent file-rewriting password change remain disabled. Enabled `admin` users issue and reset accounts at `/sso/admin/`, and an authenticated administrator may change their own password there after re-entering the current password through the same serialized writer.
- The canonical central roles are the hierarchy-closed prefix `user < developer < admin`: valid database role lists are exactly `user`, `user+developer`, or `user+developer+admin`. Legacy `users`/`owners`, unknown roles, duplicates, empty segments, and hierarchy gaps are invalid. Authelia returns the complete role list as comma-separated `Remote-Groups`; consumers must accept only the exact strings `user`, `user,developer`, or `user,developer,admin`, without whitespace or reordering.
- Authentication and account administration run as two supervised processes in one SSO container and one deployment unit. Authelia listens on loopback-published port 9091 and the administrator listens on loopback-published port 9092; Nginx remains the only public entry point. If either process exits, the supervisor must terminate the other and fail the container. The administrator remains behind Authelia authorization, an exact `admin` role check, exact header-to-database role revalidation, and a dedicated edge-to-origin shared secret. It may list sanitized profiles, create accounts, edit central roles, reset a password to a one-time generated value, let the current administrator choose a replacement password after current-password verification, and enable or disable accounts. It must never expose password hashes, pass plaintext credentials in process arguments or environment variables, or retain plaintext passwords.
- Central usernames and email addresses are immutable through the administrator UI because downstream account links use the central subject and controlled first-link email. Prefer disabling a mistaken identity and issuing a new account. An explicitly requested correction to an established identity is an operator migration: back up every affected store, stop linked writers, update exact stable user IDs with collision checks, use the central locked writer, invalidate cached SSO sessions, and verify every linked application before reopening traffic.
- The user database lives in a dedicated directory bind. Within the unified container Authelia is configured against the read-only `userdb/current/` alias, while only the administrator code writes through the parent `userdb/` alias. This is a code and mount-path discipline, not a container isolation boundary. Writers must require an exact current revision, revalidate the acting administrator and the exact forwarded roles inside the lock, serialize password hashing, validate the complete candidate, create and fsync a 0600 backup, fsync a same-directory temporary file, atomically rename it, and append password-free prepared/committed audit events. The last enabled `admin` account and the current administrator cannot be disabled or demoted; a post-commit housekeeping error must not hide an already-applied one-time credential.
- Never use mutable SSO or Redis image tags in production. Preserve the dedicated `bonifacio-sso` network and both persistent volumes during application deploys.
- `wgang` is not part of this SSO deployment. Follow `/home/cks/AGENTS.md` and do not inspect or change it unless the user separately requests that work.
- Protected portfolio routes are `/`, `/react/`, `/vue/`, `/dukkeobi/`, `/ddit-finalproject/`, `/monitor/`, `/pilgrimage/`, `/api/`, `/multtara/`, and `/feelmyrythm/`. Pilgrimage health, built assets, and its explicit UUID share routes remain narrow public exceptions; deployment health probes use loopback origins.
- Authelia's ordered ACL requires `admin` for `/sso/admin/`, `developer` for `/monitor/`, and `user` for every other protected portfolio route plus the Bonifacio landing page's `/index.html` and `/assets/` children, followed by explicit deny rules so a lower role cannot fall through to broader access.
- A Bonifacio deploy replaces the unified `bonifacioSso` container and the landing-page container from the same immutable image. It must verify both SSO loopback endpoints, preserve `bonifacioSsoRedis` and both persistent volumes, prove the Redis container ID did not change, and roll both image cutovers back on failure.
- The one-time migration from the former split `bonifacioSso` plus `bonifacioSsoAdmin` layout is a controlled structural rollout with an explicit split-layout rollback. Later application deploys use the normal unified-container rollback path. A configuration, secret, or mount migration remains a separate controlled operation.
- The Bonifacio Actions timeout must cover the host's 20-minute fleet-wide deployment-lock wait plus both image cutovers and rollback verification; keep it at 60 minutes unless the workflow is split into separate publish and deploy jobs.
- Dynamic applications must bind their native user/session to the immutable central `Remote-User` subject and compare it on every authenticated request. Trusted identity headers alone are insufficient: each edge-to-origin path must also carry its own non-public shared secret that the application verifies.
- Authentication mode is branch-bound across the portfolio: `main` and `dev` must use central SSO, while every other branch is local development mode. `scripts/portfolio-auth-mode.sh` is the canonical resolver, and explicit branch/mode mismatches must fail closed during direct startup, Compose validation, image build, and container startup.
- Production applications must not retain an independent credential, password, login-session, or account-administration system. A dynamic application may keep only the minimum central-subject projection needed to own domain records; that projection is not an identity authority and must never contain a usable password.
